## 1. 먼저 할 일 (읽기)
1. 참고 완성본 hwpx를 열어(zip → Contents/section0.xml, section1.xml, header.xml) **보고서 장 구성, 그림 13종의 역할, 포스터 표 칸 배치(표3의 "주요 인사이트" 표제 행 + 8장 카드)** 를 파악한다.
2. `차트_v2/소스(html)/design/DESIGN.md`와 `base.css`를 읽는다. 이 두 파일이 디자인 시스템이다. **우리 팀에 자체 앱/대시보드가 있으면 그 UI의 CSS 토큰(색·폰트)을 그대로 가져와 base.css의 토큰만 교체**하고, 없으면 참고 토큰을 그대로 쓴다. 핵심 변수(참고본의 CO₂·VOC에 해당하는 우리 변수)마다 색 하나를 고정한다.
3. `render.mjs`·`build_charts.py`·`figs/*.html`은 그대로 재사용 가능한 도구다(Edge 헤드리스 CDP, `<html data-kind="r|p" data-w data-h>` mm 규격, OVERFLOW 보고). 새 그림은 이 뼈대를 복사해 만든다.

## 2. 디자인 체계 (참고본과 동일하게)
- 글자는 두 단계만: 보고서 10.5pt / 제목 12pt 굵게, 포스터 17pt / 22pt 굵게. 축 눈금·범례·주석도 같은 크기. 더 작은 글자 금지.
- 그림은 실제 인쇄 크기(mm)로 만들어 **1:1로 삽입**(보고서 폭 159mm, 포스터 카드 143×85mm, 포스터 와이드 286×40/74mm).
- 색은 의미에만: 변수별 고정색, 분류(레짐 등) 색, 장치 색, 기준선 빨강 점선. 나머지는 무채색. 웹앱 패널·칩 문법(.panel .chip .num .kpi .idx) 재사용.
- 외부 라이브러리 없이 HTML + 인라인 SVG(데이터 차트는 `build_charts.py`가 data.json을 인라인하고 JS가 px 실측으로 SVG를 그림 — viewBox 금지, 글자 크기 보존).
- 포스터 8장 카드: 파란 번호 배지 ①~⑧ + 명사형 제목, **탐구 과정 순서**로 배치. 표3에 "주요 인사이트 — 탐구 과정 순서(①~⑧)" 표제 행(10mm, 글 칸에서 차감).

## 3. 문체 (가장 많이 지적받은 항목 — 반드시)
- 연구보고서 개조식: 사실 → 수치 → 해석. 구호·비유·아포리즘 금지("~하면 ~한다", "~가 아니라 ~다" 식 제목, "스위치가 아니라 와트를 믿는다" 같은 문장 금지). 긴 줄표(—) 연결 대신 짧은 문장.
- 그림 제목은 **명사형 주제어**(예: "주중·주말 시간대별 CO₂ 분포 비교", "환기 이후 CO₂의 지수적 감쇠 특성"). 결론은 캡션·본문에.
- 볼드는 항목 머리말(**수집**, **모델링**)과 핵심 수치에만.
- 수치는 확정값만, 정의를 함께(기간·방학 포함 여부·표본 수·단위). 근거 없는 인과·과장 금지("완주", "모두 유의", "구현 완료"는 근거가 있을 때만).
- 1장(배경·목적·연구 문제)은 양식 서식(14pt, ○/– 개조식, "~함"), 2·3장은 12pt 본문. 연구 문제 ↔ 가설 ↔ 결과 ↔ 시사점이 번호로 대응되게.

## 4. 에이전트 구성 (병렬, 각자 보고 후 내가 통합)
공통 브리프: DESIGN.md, base.css, data.json 구조, 확정 수치, 파일 규약. 각자 PNG를 눈으로 확인하고 OVERFLOW 0으로.
- **D1 정보 도식**: 탐구 사이클 7단계(우리 팀이 단계별로 한 일), 시스템 구성, 배선/구성도, 처리·제어 흐름(안전 원칙 포함), 원인→조치 매트릭스, 대시보드/앱 화면 설계 원칙(캡처 + 번호 핀), 주요 화면 2×2 — 보고서용·포스터용 두 벌.
- **D2 데이터 차트**: 우리 데이터의 핵심 6종(예: 하루 시계열, 요일·시간대 분포, 기준 초과율, 변수 간 관계, 분류/상태 평면, 사건 전후 변화) — `build_charts.py` 뼈대로 보고서용·포스터용 두 벌. 결측은 선을 끊고, 라벨은 직접 표기, 범례 상자 최소.
- **D3 포스터 아트디렉터**: 양식 기하(표 칸 mm) 안에서 8장 카드 배치·우선순위, 결과 칸 KPI 띠(286×40)와 스토리 패널(286×74), 방법 칸 타임라인(286×42), `poster_text.json`(칸별 글, est_lines 예산 계산 포함).
- **DX 도메인 전문가**: 본문·포스터의 모든 수치를 원자료·코드와 대조(검증표), 주장 강도(과장/소극) 점검, 논리 흐름(연구 문제–가설–결과–시사점), 용어 통일, 그림별 제목·캡션 제안, 교체용 최종 문장을 `REVIEW.md`로. 확인 불가 항목은 "확인 필요"로 표시하고 추측으로 바꾸지 않는다.
통합 시 DX의 지적을 본문·그림에 반영하고, "확인 필요"는 최종 보고에 목록으로 남긴다.

## 5. hwpx 조립 (참고본 빌더 방식)
- 양식 hwpx를 풀어 header.xml/section0.xml/section1.xml을 직접 편집(OWPML). 표 셀은 `<hp:tc>` 단위 tempered regex로만 교체, 그림은 `<hp:pic>` + BinData + content.hpf manifest(imgDim=px×75), 새 글자/문단 모양은 header.xml에 복제·itemCnt 갱신. 제목·그림 문단은 keepWithNext 복제본 사용. 양식의 빈 칸이 극소 글자(3pt)일 수 있으니 charPr를 명시.
- 포스터는 양식 표 칸에 글(한/글 텍스트 20/22pt)과 PNG를 넣는다. 칸별 줄 수를 est_lines로 추정해 **칸 높이 −4mm 안**에 들도록 assert. 양식 표의 행을 추가할 때는 다른 행에서 높이를 빼 표 전체 높이를 유지한다.
- 산출: 바탕화면 `…/<팀>/결과보고서 및 포스터_<팀>_학생버전.hwpx`, `차트/`(보고서용·포스터용 PNG, html 소스, README, `_한눈에_*.png`), `HANDOFF.md`, `REVIEW.md`.

## 6. 검증
1. `node render.mjs` 전부 `ok`, 폰트 로그에 IBM Plex Sans KR(또는 교체한 폰트).
2. hwpx 구조 검사: mimetype 첫 항목, XML 파싱, charPr/paraPr 참조 누락 0, BinData ↔ manifest 일치, 표 행 높이 합 = 표 높이.
3. **한/글에서 열어 PDF로 내보내 1쪽 포스터·그림 배치를 눈으로 확인**(COM 자동화는 보안 대화상자·화면 잠금 때문에 불안정 — 사람이 연다). 넘침은 글 줄이기 → 그림 높이 축소 순으로.
4. 보고서 그림의 글자가 본문보다 작지 않은지, 색이 앱 화면과 같은지, 제목이 전부 명사형인지 마지막으로 훑는다.

## 7. 주의 (참고본에서 겪은 함정)
- 그림 글자 9pt로 만들면 본문(12–14pt) 옆에서 읽히지 않는다. 생성 시 크기 = 삽입 크기.
- 통계 창에 방학·휴일이 섞이면 "수업시간" 같은 표현이 과소/과대가 된다. 기간 정의를 수치 옆에 적는다.
- 분석 코드의 전처리 정의와 운영 시스템의 규칙(예: 품질 검사)이 다르면 본문에서 둘을 구분한다.
- 공개 저장소에는 학생·교사 이름이 든 파일(hwpx·빌더·poster_text.json)을 올리지 않는다.
- Edge 헤드리스는 Git Bash에서 파일이 안 생길 수 있다 — 참고본 `render.mjs`(node + CDP) 사용. 사용자 데스크톱 PC의 한/글이 열려 있을 때 COM으로 접근하지 않는다.

마지막 보고에는 산출 파일 경로, 그림 목록, 포스터 칸별 예산 표, DX 검증에서 남은 "확인 필요" 목록, 사용자가 결정해야 할 항목(헤드라인 수치 선택 등)을 적는다.
