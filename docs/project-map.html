노드를 선택하세요

세로 열은 "누가 시작시키는가"에서 "누가 최종 소비하는가"까지의 순서입니다. 노드를 클릭하면 그 파일의 역할 요약과, 무엇을 부르고 누가 부르는지가 나옵니다.

공용 모듈 열은 스스로 실행되는 일이 없습니다 — 다른 스크립트가 import 해서 함수만 빌려 씁니다.

유일한 쓰기 주체 (writer)읽기만 (reader)테이블 클릭 → 컬럼 + 같은 키로 이어지는 테이블

테이블을 선택하세요

DB 파일마다 쓰기 주체(writer)를 하나로 두면 잠금 경합이 없고, 파일이 잘못됐을 때 의심할 프로그램이 하나로 좁혀집니다.

파일 사이 점선은 외래키가 아니라 같은 값(보통 날짜·시각 문자열)으로 코드에서 조인하는 관계입니다.

"API" 는 스크립트도, DB 호출도 아닙니다

API 는 "서버가 클라이언트에게 약속한 주소와 응답 모양" 입니다. 어떤 스크립트가 만들었는지, 뒤에서 DB 를 읽는지 JSON 파일을 읽는지는 약속에 들어가지 않습니다. 그래서 문서 제목이 "API 계약" 입니다.

스크립트계산해서 저장
데이터 파일결과가 놓이는 곳
엔드포인트서버가 여는 문
GET /api/…
소비자브라우저가 fetch

엔드포인트 = 파이프라인의 끝이 아니라 서버 쪽 "문"

엔드포인트는 HTTP 요청이 도착하는 주소 하나(메서드 + 경로)입니다. 배치 파이프라인(타이머→스크립트→파일)의 출력이 아니라, 그와 별개의 요청–응답 축에서 서버가 열어 둔 입구입니다. 라우터 파일 안의 @router.get("/api/…") 함수 하나가 엔드포인트 하나이고, 요청이 올 때마다 실행되어 그때 파일이나 DB 를 읽습니다.

API추상적 약속. "이 주소에 이런 JSON 이 온다"
엔드포인트그 약속의 한 줄. 메서드+경로 하나 = 라우터 함수 하나
라우터엔드포인트를 묶은 파일
스크립트 / 잡타이머가 돌리는 독립 프로세스. HTTP 와 무관, 파일을 남기고 종료
혼동이 생기는 이유 — 스크립트가 남의 API(NEIS, Guardian…)를 호출할 때 우리 스크립트는 클라이언트입니다. API 계약에서는 방향이 반대로 우리 서버가 내주는 쪽입니다. "스크립트 = 클라이언트 쪽, 엔드포인트 = 서버 쪽"으로 자리를 나누면 헷갈리지 않습니다.
